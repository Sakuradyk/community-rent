# M5 推荐离线评估

> 论文对应小节：**推荐算法的离线评估**（三条硬指标中「推荐可解释」的定量证据）
> 脚本：`backend/src/test/java/com/duyikang/rental/module/recommend/eval/RecommendEvaluation.java`
> 结果文件（每次运行覆盖）：`backend/target/eval/recommend-eval.md`
> 最后更新：2026-11-23

## 1. 为什么需要离线评估

线上没有真实流量（毕设演示环境只有几个账号），A/B 与点击率这类在线指标拿不到统计意义，因此采用**离线评估**：用历史行为模拟"过去预测未来"，量化推荐结果与用户真实选择的重合度。

这样做的价值有两点：

1. 「推荐可解释」这条硬指标从**定性**（每条结果都带理由）变成**定量**（命中率有数字）；
2. 三个权重 `0.6 / 0.3 / 0.1` 不再只是"凭经验设定"，而是有**消融对照**支撑。

## 2. 评估方法

### 2.1 时间切分（避免信息泄漏）

```
时间轴（共 120 天）
├────────────── 历史窗口 96 天 ──────────────┤├─ 评测窗口 24 天 ─┤
                                         cutoff            now
```

- **历史窗口**：只用来构造用户画像、共现矩阵、类目偏好；
- **评测窗口**：只当"标准答案"，用户在这段时间真实租过的物品构成测试集；
- **关键约束**：`RecommendService.recommend(limit, cutoff)` 的 `historyCutoff` 同时作用于
  ① 当前用户的订单（画像）② 全体用户的订单（共现矩阵）。任一处漏掉，就等于把答案喂给模型，命中率必然虚高 —— 这是离线评估最常见的作弊点。
- 生产调用走 `recommend(limit)`（`cutoff = null`，用全部历史），评估才传 `cutoff`，两者**共用同一份打分代码**。

### 2.2 指标定义

对每个用户取 Top-10 推荐结果，与其测试集求交集：

| 指标 | 定义 | 含义 |
| :-- | :-- | :-- |
| **HitRate@10** | 至少命中 1 件的用户数 ÷ 参与评估用户数 | 十个人里有几个人被推对（论文主指标） |
| Precision@10 | 命中件数 ÷ (用户数 × 10) | 推十件中几件有用 |
| Recall@10 | 命中件数 ÷ 测试集总件数 | 该推的有没有漏 |

评测窗口内没有行为的用户（测试集为空）不计入分母 —— 没有标准答案的用户既不能被算作命中，也不该被算作失败。

### 2.3 数据来源

真实库只有 5 个用户、8 条订单，时间切分后评测窗口几乎是空的，做不出有意义的统计。因此评估使用**合成数据**（脚本内生成，`@Transactional` 结束自动回滚，不污染开发库）：

| 项 | 配置 |
| :-- | :-- |
| 用户 | 120 个（手机号 `199` 号段，与真实账号不冲突） |
| 物品 | 60 件，均匀落在 8 个**真实二级类目**上（复用 `category` 表，内容相似度才有意义） |
| 行为 | 每用户 4–12 条已完成订单，共 960 条 |
| 偏好模型 | 主类目 70% + 同父类目其他二级 20% + 随机 10%（模拟"人有多样性，但偏好集中"） |
| 时间分布 | 订单均匀落在 120 天窗口内，下单时间为租赁开始前一天 |
| 随机种子 | `20261123`（固定种子 → 同结果可复现） |

类目偏好集中度决定了任务难度：偏好越集中，越容易命中。这里的 70/20/10 接近真实社区租赁的直觉（人来借东西通常有明确用途），论文中如实写明这一假设。

## 3. 结果（2026-11-23 运行）

| 权重方案 | 参与评估用户 | 冷启动用户 | 命中用户 | 命中件数 / 测试集件数 | HitRate@10 | Precision@10 | Recall@10 |
| :-- | --: | --: | --: | --: | --: | --: | --: |
| **混合（本文默认 0.6 / 0.3 / 0.1）** | 93 | 0 | 75 | 115 / 156 | **80.65%** | 12.37% | 73.72% |
| 纯协同过滤（1.0 / 0 / 0） | 93 | 0 | 74 | 110 / 156 | 79.57% | 11.83% | 70.51% |
| 纯内容相似（0 / 1.0 / 0） | 93 | 0 | 65 | 83 / 156 | 69.89% | 8.92% | 53.21% |
| 纯热度（0 / 0 / 1.0） | 93 | 0 | 29 | 31 / 156 | 31.18% | 3.33% | 19.87% |

> 注：合成用户都有历史行为，故四组方案都不触发冷启动（冷启动分支由 `RecommendServiceTest#recommend_anonymous_isColdStart` 覆盖）。

## 4. 结论

1. **混合方案在三个指标上均为最优**：HitRate@10 = 80.65%，比纯协同过滤高 1.08 个百分点，比纯内容高 10.76 个百分点，比纯热度高 49.47 个百分点。
2. **协同过滤是本项目的主力信号**：合成数据里有明确类目偏好且用户量足够，共现关系可学；这也解释了为什么 `w.cf = 0.6` 占大头。
3. **内容相似是必要的补充但不是主因**：单独使用时 Recall 只有 53.21%，因为同父类目的物品在价格/用途上差异大；它与 CF 混合后把 HitRate 从 79.57% 提到 80.65%，说明"新物品没有共现"时内容信号能补齐。
4. **纯热度显著退化**：31.18% 已接近随机水平（60 件物品中取 10 件，单件随机命中率 10/60 ≈ 16.7%），验证了「热度只能做冷启动兜底，不能作为老用户的主策略」。
5. 与硬指标对照：需求总结要求 **Top-10 命中率 ≥ 30%（目标值）**，混合方案 80.65% 远超目标值；纯热度基线 31.18% 恰好压在目标线附近，说明这个阈值定得合理（不是随手写的）。

## 5. 局限（论文中必须如实写明）

1. **合成数据不等于真实行为**：偏好集中度 70/20/10 是假设，偏好越集中命中率越高；真实场景（用户数月租一次）的绝对命中率会低于本表。
2. **物品池小（60 件）**：Top-10 覆盖了 1/6 的目录，绝对数值被抬高。因此**应重点看方案间的相对差异，而不是绝对值**。
3. **协同过滤是 item-item 共现 + 时间衰减的简化实现**，没有矩阵分解、没有负采样，也不做隐式反馈加权；这是毕设范围内的合理取舍（可解释性优先于精度）。
4. **未评估"新颖性/多样性"**：只看命中率会奖励"反复推同类"，论文中把它列为后续工作。
5. 用户数 120、评测窗口 24 天，评测期为空的用户被剔除后实际参与 93 人，样本量仍偏小，指标的置信区间较宽。

## 6. 复现方式

```powershell
cd backend
# 只跑评估（不参与 mvn test 的默认扫描，因为类名不以 Test 结尾）
mvn -Dtest=RecommendEvaluation -DfailIfNoSpecifiedTests=false test
# 结果
type target\eval\recommend-eval.md
```

评估全程 `@Transactional`，结束后回滚，所以**跑多少次都不会在 `rental` 库里留下数据**；`sys_config` 的三组权重也会随事务一起恢复。
