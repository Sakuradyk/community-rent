# 接口文档（契约唯一真源）

> **地位**：本文件是前后端之间的契约唯一真源。后端 DTO/VO 字段名、前端页面里出现的字段名，都必须能在这里找到出处；找不到就是契约没冻结，先补这里再写代码。
> **改法**：加字段 → 双写（本文件 + 后端 VO + 前端 `constants.js` 若涉及枚举）；改字段名/类型 → 同一提交内改完前后端，提交说明首行打 `CONTRACT CHANGE:`；删字段 → 先确认前端已无引用。
> **配套**：`PROJECT_RULES.md` §7（响应体与错误码段位）、`docs/前后端并行开发方案.md`（切片纪律）。

## 0. 全局约定（切片 0 冻结，之后不许单独改）

| 项 | 约定 | 前端落地位置 |
| :-- | :-- | :-- |
| 统一响应体 | `{ code, message, data, traceId }`；`code === 0` 为成功，其余为失败 | `web-*/src/api/request.js` |
| 成功判定 | **只认 `code === 0`**，不用 `message` 判成败 | 同上 |
| 成功时的 `data` | 业务载荷（对象/数组）；无返回值的接口 `data` 为 `null` | 各 `api/*.js` |
| 失败时的 `data` | 一般为 `null`；**唯一例外是 4090**（见 §0.5） | 下单页 |
| `traceId` | 由后端 `TraceIdFilter` 生成，同时写入响应头 `X-Trace-Id`；排查问题时报这个值 | — |
| 认证头 | `Authorization: Bearer {accessToken}` | `request.js` 请求拦截器 |
| 分页入参 | `pageNum`（**从 1 起**）、`pageSize`（默认 10，**上限 100**） | `utils/constants.js` → `LIMITS` |
| 分页响应 | `{ list, total, pageNum, pageSize }`（字段名就是 `list`，不是 `records`） | 列表页 |
| 主键类型 | 所有 `Long` id 序列化为**字符串**（`"12"`）；前端禁止 `Number(id)`、禁止对 id 做算术 | 全站 |
| 日期 | `YYYY-MM-DD`（例 `2026-11-20`） | `dayjs().format('YYYY-MM-DD')` |
| 时刻 | `YYYY-MM-DD HH:mm:ss`（例 `2026-11-20 14:30:00`） | `utils/format.js` |
| 金额 | JSON number，两位小数（`25.00`）；**前端只展示不算钱**，算钱只有 `/api/orders/quote` | `formatMoney()` |
| 静态图片 | 后端返回相对路径 `/uploads/202611/xxx.png`，开发期由 Vite proxy 转发到 8080 | `vite.config.js` |

### 0.1 错误码（切片已用到的）

| code | 含义 | 前端处理 |
| :-- | :-- | :-- |
| 0 | 成功 | — |
| 1001 | 未登录 / 缺少令牌 | 清登录态 → 跳登录页 |
| 1002 | 无权限（如非管理员访问 `/api/admin/**`） | 提示，不跳转 |
| 1003 | 令牌无效（签名/格式/类型错误） | 清登录态 → 跳登录页 |
| 1004 | 令牌已过期 | 清登录态 → 跳登录页 |
| 1005 | 手机号或密码错误（**故意合并**，防手机号枚举） | 表单下方提示 |
| 1006 | 账号已禁用 | 提示 |
| 2001 | 参数不合法（含「手机号已注册」「所选社区不存在」） | 表单提示 |
| 2004 | 文件类型不支持 | 上传处提示 |
| 2005 | 文件超出大小限制 | 上传处提示 |
| 4090 | 时段冲突（带明细，见 §0.5） | 日历标红 + 建议区间 |
| 5000 | 系统异常 | 通用提示 |

### 0.5 4090 的响应形状（K2 对外契约，已冻结）

```json
{
  "code": 4090,
  "message": "该时段已被占用，请选择其他日期",
  "data": {
    "itemId": "2",
    "conflictDates": ["2026-11-20", "2026-11-21"],
    "suggestRanges": [{ "startDate": "2026-11-24", "endDate": "2026-11-26" }]
  },
  "traceId": "4c949f0bada44412"
}
```

前端拿到 4090 只做两件事：把 `conflictDates` 在日历上标红；把 `suggestRanges` 渲染成「试试这几天」按钮。**该形状变更属于破坏性变更**。

## 1. 账号与公共字典（切片 1，已实现并实测）

### 1.1 注册

`POST /api/auth/register` · 无需登录

| 字段 | 类型 | 必填 | 约束 |
| :-- | :-- | :-- | :-- |
| `phone` | string | 是 | `^1[3-9]\d{9}$` |
| `password` | string | 是 | 6–20 位 |
| `nickname` | string | 是 | 2–16 字 |
| `communityId` | string \| null | 否 | 必须是 `GET /api/communities` 返回的 id；不选传 `null` |

响应 `data` = **LoginVO**（见 §1.3）。初始信誉分读 `credit_policy.init_score`（当前 80），不接受前端传分。

错误：`2001`（手机号已注册 / 所选社区不存在 / 参数校验失败）。

```json
// 请求
{ "phone": "13900002001", "password": "123456", "nickname": "测试用户", "communityId": "1" }
// 响应 data
{
  "accessToken": "eyJhbGciOi...",
  "refreshToken": "eyJhbGciOi...",
  "expiresIn": 7200,
  "user": { "id": "12", "nickname": "测试用户", "phone": "139****2001",
            "avatarUrl": null, "communityId": "1", "creditScore": 80,
            "status": "NORMAL", "createdAt": "2026-11-17 19:05:12" }
}
```

### 1.2 登录

`POST /api/auth/login` · 无需登录

| 字段 | 类型 | 必填 |
| :-- | :-- | :-- |
| `phone` | string | 是 |
| `password` | string | 是 |

响应 `data` = **LoginVO**。错误：`1005`（手机号不存在或密码错误，两者同一码）、`1006`（账号已禁用）。
登录成功会更新 `user.last_login_at`。

### 1.3 LoginVO（结构定义）

| 字段 | 类型 | 说明 |
| :-- | :-- | :-- |
| `accessToken` | string | 访问令牌，有效期 2 小时，claims：`sub/username/role/typ=access` |
| `refreshToken` | string | 刷新令牌，有效期 7 天，claims：`sub/jti/typ=refresh`（**故意不带角色**） |
| `expiresIn` | number | access 剩余秒数（7200） |
| `user` | UserVO | 见 §1.6 |

### 1.4 刷新令牌

`POST /api/auth/refresh` · 无需登录（凭 refreshToken 本身）

| 字段 | 类型 | 必填 |
| :-- | :-- | :-- |
| `refreshToken` | string | 是 |

响应 `data` = **LoginVO**，且**轮换**：旧的 refreshToken 立即失效。
错误：`1003`（无效 / 已登出 / 服务端白名单不匹配 / 误把 accessToken 传来）、`1006`（账号已禁用）。

### 1.5 登出

`POST /api/auth/logout` · 需登录

作废服务端 refresh 白名单（Redis `auth:refresh:{userId}`）。响应 `data` 为 `null`。

### 1.6 当前用户

`GET /api/users/me` · 需登录 → `data` = **UserVO**

| 字段 | 类型 | 说明 |
| :-- | :-- | :-- |
| `id` | string | 主键（字符串） |
| `nickname` | string | 昵称，可改 |
| `phone` | string | **已脱敏**，形如 `139****2001` |
| `avatarUrl` | string \| null | 头像相对路径 `/uploads/...` |
| `communityId` | string \| null | 所在小区；未选择为 `null` |
| `creditScore` | number | 信誉分，区间 [0,100] |
| `status` | string | `NORMAL` / `DISABLED` |
| `createdAt` | string | 注册时刻 `YYYY-MM-DD HH:mm:ss` |

`PUT /api/users/me` · 需登录

| 字段 | 类型 | 必填 | 约束 |
| :-- | :-- | :-- | :-- |
| `nickname` | string | 否 | 2–16 字（传了就校验） |
| `avatarUrl` | string | 否 | 必须是本系统上传接口返回的路径 |
| `communityId` | string \| null | 否 | 传 `null` 表示清空 |

响应 `data` 为 `null`；前端改完再调 `GET /api/users/me` 校准（不要自己拼本地状态）。

### 1.7 社区字典

`GET /api/communities` · **匿名可读** → `data` = 数组

```json
[ { "id": "1", "name": "阳光花园", "district": "城东街道" },
  { "id": "2", "name": "绿洲家园", "district": "城东街道" } ]
```

只返回 `enabled = 1` 的社区，按 `sort_no`、`id` 升序。停用的社区不会出现在这里——这也是「注册时选不到紫竹园」的原因。

### 1.8 图片上传

`POST /api/files/upload` · 需登录 · `multipart/form-data`，字段名 **`file`**

| 约束 | 值 |
| :-- | :-- |
| 大小 | ≤ 5MB（超限返回 `2005`） |
| 类型 | `jpg` / `jpeg` / `png` / `webp`（其余返回 `2004`） |
| 存储 | `{file.root}/{yyyyMM}/{uuid}.{ext}`，**丢弃原文件名**（防路径穿越） |
| 返回 | `{ "url": "/uploads/202611/b8818f21....png", "size": 70 }` |

前端禁止手写 `Content-Type: multipart/form-data`（boundary 会丢），用 `FormData` 交给 axios。

### 1.9 忘记密码（重置密码）

`POST /api/auth/reset-password` · **无需登录**（用户正因为进不去才来重置）

| 字段 | 类型 | 必填 | 约束 |
| :-- | :-- | :-- | :-- |
| `phone` | string | 是 | `^1[3-9]\d{9}$` |
| `nickname` | string | 是 | 2–16 字，须与注册时一致 |
| `communityId` | string \| null | 否 | **注册时选过社区则必须一致**；注册时没选就传 `null` |
| `newPassword` | string | 是 | 6–20 位 |

响应 `data` 为 `null`。

**错误码与安全约定**

| 码 | 场景 |
| :-- | :-- |
| `2001` | 手机号 / 昵称 / 社区任一不一致 —— **三种情况返回同一句文案**「手机号、昵称或社区与注册信息不一致」 |
| `1006` | 账号已停用 |

- 统一文案是刻意的：若分别提示「手机号不存在」「昵称不对」，本接口就成了手机号/昵称的探测工具。
- 重置成功后**该用户所有 refresh 令牌立即作废**（Redis 白名单被删）：改密意味着原主人可能已失去对账号的控制权，旧令牌必须一起失效。
- 本项目无短信/邮件通道（需求总结 §10），故用「知识校验」代替验证码。**这不能阻止知道对方昵称与小区的人重置密码**，属毕设范围内的已知取舍，已备案到需求总结 §14.1。

## 2. 物品（切片 2，已冻结 2026-11-18）

> 本切片 10 个接口。**本节字段名一经实现不得单方面修改**，改动走 §0 的 `CONTRACT CHANGE:` 规则（三处同步 + 提交首行标注）。
> 排序里的「同小区 > 同片区」受 `sys_config.community.priority.enabled` 控制，置 `0` 时该档整体失效、退回纯热度排序（即可做 FR-M5-01 要求的前后对比）。

### 2.0 本切片新增的字段约定

| 约定 | 冻结值 | 为什么这样定 |
| :-- | :-- | :-- |
| 图片入参 | `imageUrls: string[]`，1–5 张，元素为 `/uploads/...` 相对路径（先调 §1.8 拿） | 前端不管封面逻辑 |
| 封面 | **后端取 `imageUrls[0]` 写 `item.cover_url`**，前端不传 `coverUrl` | 列表页零 join；多图排序是 P2，上传顺序即展示顺序 |
| 图片出参 | 列表只给 `coverUrl`；详情给 `images: [{id,url}]`（按 `id` 升序） | 列表不为图片查第二张表 |
| 审核字段 | 入参 `approved: boolean` + `remark: string`；出参 `auditRemark` | 「驳回原因」就是 `remark`，不另起 `reason` |
| 状态枚举 | `PENDING / ON_SHELF / OFF_SHELF / RENTED / MAINTAINING / REJECTED` | 与 `web-user/src/utils/constants.js` 的 `ITEM_STATUS` 一一对应 |
| 金额 | JSON number，两位小数，**只展示不算钱** | 算钱走切片 3 的 `/api/orders/quote`（F1） |
| 「进行中订单」 | `CONFIRMED / IN_USE / OVERDUE` 三态之一 | 这三态才占时段（需求总结 §6），`PENDING` 不占 |

### 2.1 发布物品 `POST /api/items`（需登录）

| 字段 | 类型 | 必填 | 约束 |
| :-- | :-- | :-- | :-- |
| `title` | string | 是 | 1–64 字 |
| `categoryId` | string(Long) | 是 | 必须存在、`level = 2`、`status = NORMAL` |
| `description` | string | 否 | ≤1000 字（推荐内容特征的来源） |
| `communityId` | string(Long) | 是 | 必须存在且 `enabled = 1` |
| `dailyPrice` | number | 是 | `> 0`，且落在 `fee_policy.price_min ~ price_max` |
| `deposit` | number | 是 | `>= 0`，且落在 `ratio_min × 日租金 ~ ratio_max × 日租金` |
| `overdueRate` | number | 是 | 落在 `fee_policy.rate_min ~ rate_max` |
| `imageUrls` | string[] | 是 | 1–5 个，每个须匹配 `^/uploads/\d{6}/[0-9a-f]{32}\.(jpg\|jpeg\|png\|webp)$` |

- 成功：`{"code":0,"data":{"id":"12"}}`，状态落库为 `PENDING`（待审），`cover_url = imageUrls[0]`。
- 错误：`2001`（必填/格式/类目不存在/类目不是二级/社区不存在或已停用）、`4001`（三个价格任一越界，message 指明是哪个字段）。
- **不做**：草稿箱、保存后继续编辑不重审。

### 2.2 编辑物品 `PUT /api/items/{id}`（需登录）

- 入参同 §2.1（整体替换，不是局部更新）。
- 仅归属人可编辑，否则 `3008`；仅 `PENDING / OFF_SHELF / REJECTED` 可编辑，其余 `3003`。
- 编辑后**状态一律回到 `PENDING`** 并清空 `audit_remark / audit_admin_id / audit_time`（驳回后改完即重提，不需要额外的「重新提交」接口）。
- 图片按 `imageUrls` 顺序整体重写：删旧行、插新行，`cover_url = imageUrls[0]`。

### 2.3 上下架 `PUT /api/items/{id}/shelf`（需登录）

| 字段 | 类型 | 说明 |
| :-- | :-- | :-- |
| `onShelf` | boolean | `true` = 上架，`false` = 下架 |

- 仅归属人，否则 `3008`。
- `true`：要求当前 `OFF_SHELF`，改 `ON_SHELF`；`false`：要求当前 `ON_SHELF` 且**无进行中订单**，改 `OFF_SHELF`。
- 其余状态（`PENDING / REJECTED / RENTED / MAINTAINING`）→ `3003`，message 说明当前状态不可上下架。

### 2.4 物品列表 `GET /api/items`（**匿名可访问**）

| 参数 | 类型 | 说明 |
| :-- | :-- | :-- |
| `keyword` | string | 匹配 `title` 或 `description`，`LIKE %kw%` |
| `categoryId` | string(Long) | 传一级类目时自动含其二级 |
| `communityId` | string(Long) | 精确等于 |
| `minPrice` / `maxPrice` | number | 对 `daily_price` 过滤，两端都可单给 |
| `startDate` / `endDate` | `YYYY-MM-DD` | **两个都给才生效**；用 §0 的半开区间判定 `[start,end)`，禁止前端二次过滤 |
| `pageNum` | int | 从 1 起，默认 1 |
| `pageSize` | int | 默认 10，上限 100 |

> **可见性口径（已定，2026-11-19）**：列表**只返回 `status = ON_SHELF`** 的物品。因此物品被出租方「标记已取用」（`RENTED`）后**从列表消失**，取消或归还后恢复 `ON_SHELF` 重新出现；租期内的**其他日期不可被他人预约**（这是刻意的简化，答辩口径：「物品租出去了就不在架上，回来再上架」）。
> 详情接口仍可打开（只有 `PENDING` / `REJECTED` 对他人隐藏），日历照常显示占用日期。**配套义务**：`return` 实现时必须把物品从 `RENTED` 恢复（按损耗决定 `ON_SHELF` 或 `MAINTAINING`），否则物品会永久卡在 `RENTED`。

`ItemCardVO`（`PageResult<ItemCardVO>` 里的元素）：

| 字段 | 类型 | 说明 |
| :-- | :-- | :-- |
| `id` | string | |
| `title` | string | |
| `coverUrl` | string | 可能为 null（历史数据），前端显示占位图 |
| `dailyPrice` / `deposit` | number | 两位小数 |
| `categoryId` / `categoryName` | string | |
| `communityId` / `communityName` | string | |
| `rentCount` | int | 热度 |
| `available` | boolean \| null | **仅在传了 `startDate & endDate` 时有值**；null 表示"没问可租性" |

- 只返回 `status = 'ON_SHELF'` 的物品。
- 排序（`community.priority.enabled = 1` 且已登录且有 `community_id`）：`同小区 DESC, 同片区 DESC, rent_count DESC, created_at DESC, id DESC`；未登录或无社区时跳过前两档。
- 403/401 不出现：该接口 `permitAll`，带不带 token 都能用。

### 2.5 物品详情 `GET /api/items/{id}`（匿名可访问）

`ItemDetailVO`：

| 字段 | 类型 | 说明 |
| :-- | :-- | :-- |
| `id` / `title` / `description` | string | |
| `categoryId` / `categoryName` | string | |
| `communityId` / `communityName` | string | |
| `dailyPrice` / `deposit` / `overdueRate` | number | 逾期费率 `0.5000` 形如 0.5 |
| `lossValue` | number | 四位小数 |
| `maintenanceState` | string | `NORMAL`（< `loss_policy.maintain_threshold`）/ `MAINTAIN`（≥ maintain）/ `REPAIR`（≥ repair） |
| `status` | string | 六态之一 |
| `images` | `[{id,url}]` | 按 `id` 升序 |
| `owner` | `{id,nickname,avatarUrl,creditScore,communityName}` | **绝不返回手机号** |
| `rentCount` / `viewCount` | int | 详情每次读取 `view_count + 1` |
| `createdAt` | string | `YYYY-MM-DD HH:mm:ss` |

- 可见性：`ON_SHELF / OFF_SHELF / RENTED / MAINTAINING` 任何人可看；`PENDING / REJECTED` **仅归属人与管理员**可看，其他人返回 `3004 物品不存在`（不泄露"存在但被驳回"）。
- 检修中（`maintenanceState != NORMAL` 或 `status = MAINTAINING`）照常可见，但下单会在切片 3 被拒（`3003`）。

### 2.6 占用日历 `GET /api/items/{id}/calendar`（匿名可访问）

| 参数 | 类型 | 必填 | 说明 |
| :-- | :-- | :-- | :-- |
| `month` | `YYYY-MM` | 是 | 非法格式 → `2003` |

响应 `data`：

```json
{
  "itemId": "2",
  "month": "2026-11",
  "occupiedDates": ["2026-11-20", "2026-11-21", "2026-11-22"],
  "availableDates": ["2026-11-01", "2026-11-02", "..."]
}
```

- `occupiedDates` = `order_occupancy` 关联 `rental_order` 中状态 ∈ `CONFIRMED/IN_USE/OVERDUE` 且落在该月的日期集合（升序、去重）。
- `availableDates` = 该月 1 日到月末 **补齐**（前端直接按数组标色，不做日期算术）。
- 这是 FR-M1-05 的唯一实现，切片 3 的可租日期筛选必须复用它，不得另写区间逻辑。

### 2.7 我的物品 `GET /api/items/mine`（需登录）

- 参数：`status`（可选，六态之一）、`pageNum`、`pageSize`。
- 返回 `PageResult<MyItemVO>`；`MyItemVO` = `ItemCardVO` + `status` + `statusLabel` + `auditRemark` + `createdAt` + `imageCount`。
- 排序：`created_at DESC`（自己的东西按发布时间倒序，不做社区优先）。

### 2.8 删除物品 `DELETE /api/items/{id}`（需登录）

## 3. 订单与下单（切片 3，已冻结 2026-11-19）

### 3.0 本切片的字段与口径约定

| 项 | 约定 | 为什么这么定 |
| :-- | :-- | :-- |
| 租期区间 | **半开区间 `[startDate, endDate)`**：`11-20 → 11-23` 表示占用 20、21、22 三天 | 归还日当天不占用，物品当天可以被下一位租；闭区间会让每单多占一天，边界永远对不齐 |
| 计费天数 | `rentDays = endDate − startDate`（天，必须 ≥ 1） | 与占用天数、`rental_order.rent_days` 完全一致，三处一个数 |
| 租期上限 | `rentDays ≤ order.max_days`（当前配置 30） | 家庭闲置租一个季度不现实，且便于答辩演示与压测 |
| 金额构成 | `rentAmount = dailyPrice × rentDays`；`totalAmount = rentAmount + deposit`；**不收服务费** | 母版费用模型只有「租金 + 押金 + 逾期费 + 损耗费」，凭空加服务费等于改立论 |
| 金额归属 | 前端**只展示、不算钱**；唯一算钱入口是本切片 §3.1 | 规则 F1；两处各算一遍必然对不上 |
| 价格快照 | 下单时把 `dailyPrice / deposit / overdueRate` 写进订单行 | 之后出租方改价不影响已成立的订单（需求 §6） |
| 初始状态 | 创建即 `PENDING`，**并且立即占用时段** | 若「待确认不占时段」，同一物品在确认前可被重复下单，K2 的"同一时段零放行"当场破；代价是「取消必须释放占用」，见切片 4 |
| 订单号 | `R + yyyyMMdd + 4 位当日序号`，如 `R202611190001` | 与母版示例一致；人眼可读、可按天排序 |
| 「进行中」 | `CONFIRMED / IN_USE / OVERDUE` | 与 §2.0 的定义同一套，日历、可租性、下架判断共用 |

### 3.2 创建订单 `POST /api/orders`（需登录）

**入参**

| 字段 | 类型 | 必填 | 说明 |
| :-- | :-- | :-- | :-- |
| `itemId` | string | 是 | 物品 id |
| `startDate` | string | 是 | `YYYY-MM-DD` |
| `endDate` | string | 是 | `YYYY-MM-DD`，**不含**当天 |
| `remark` | string | 否 | 备注，≤255（如「周五晚上来取」） |

**出参**

```json
{
  "id": "5",
  "orderNo": "R202611190001",
  "status": "PENDING",
  "statusLabel": "待确认",
  "startDate": "2026-11-24",
  "endDate": "2026-11-26",
  "rentDays": 2,
  "rentAmount": 120.00,
  "depositAmount": 500.00,
  "totalAmount": 620.00
}
```

**服务端行为（顺序即代码里的校验顺序，失败就用第一个命中的码）**

1. 参数格式 → `2001` / `2003`
2. 物品存在且对当前用户可见 → 否则 `3004`
3. 不是自己的物品 → 否则 `3006`
4. 物品状态必须是 `ON_SHELF` → 否则 `3003`
5. 日期合法（`startDate < endDate`、`startDate ≥ 今天`）、`rentDays ≤ order.max_days` → 否则 `2001`
6. **服务端重新算钱**（不信任前端传的金额，前端也不传金额）、快照价格
7. 抢 Redis 锁 `lock:item:{itemId}` → 抢不到重试 500ms 后判 `4090`
8. 事务内：`INSERT rental_order` → **按 `[startDate, endDate)` 逐日 `INSERT order_occupancy`**
9. 唯一索引 `uk_occupancy` 冲突（并发后手）→ 兜底转 `4090`

**并发承诺（K2 断言口径）**：同一物品、同一时段、50 个请求同时下单 → **成功恰好 1 单**，其余全是 `4090`，不允许出现 `5003` / `5000`；`order_occupancy` 中该时段行数 = 订单天数，且无重复日期。

**错误码**：`2001`、`3003`、`3004`、`3006`、`4090`。

## 4. 订单状态流转（切片 4，已冻结 2026-11-19）

### 4.0 状态机与口径

```
PENDING ──confirm──> CONFIRMED ──pickup──> IN_USE ──(逾期扫描)──> OVERDUE
   │                    │                    │                    │
   └──cancel────────────┴──cancel──> CANCELLED│                    │
                                              └────return─────────┴──> COMPLETED
```

| 口径 | 规定 |
| :-- | :-- |
| 谁能做 | `confirm` / `pickup` 只限**出租方**；`cancel` 限**订单双方**（管理员可代为取消）；`scan-overdue` 只限管理员 |
| 状态迁移 | 一律用条件更新（`WHERE id=? AND status=<旧状态>`），受影响行数为 0 → **3001**，附带当前状态文案 |
| 谁释放占用 | 只有 **cancel** 与 **return**。`confirm` / `pickup` / `scan-overdue` 都不动 `order_occupancy` |
| 物品状态联动 | `pickup` → 物品 `RENTED`；`cancel` → 若物品是 `RENTED` 则回 `ON_SHELF` |
| 幂等 | 重复点同一动作：第一次成功，第二次因状态已变 → 3001（前端刷新即可，不会双写） |
| 归还与结算 | **不在本切片**：`return` 要同时算逾期费/损耗费并生成结算单，随切片 5 一起做（见 §4.6） |

### 4.1 确认出租 `POST /api/orders/{id}/confirm`（需登录，仅出租方）

- 入参：无 body
- 成功：`{"code":0,"message":"成功","data":null}`
- 副作用：`status=CONFIRMED`、`confirmed_at=NOW()`
- 错误：`3005` 订单不存在、`3008` 非出租方、`3001` 当前不是 `PENDING`

### 4.2 标记已取用 `POST /api/orders/{id}/pickup`（需登录，仅出租方）

- 入参：无 body
- 成功：`{"code":0,"message":"成功","data":null}`
- 副作用：`status=IN_USE`、`in_use_at=NOW()`、物品转 `RENTED`
- 错误：`3005` / `3008` / `3001`（当前不是 `CONFIRMED`）

### 4.3 取消订单 `POST /api/orders/{id}/cancel`（需登录，双方或管理员）

```json
{ "reason": "临时不需要了" }
```

- `reason` 可省略（≤255 字），为空时记为「用户主动取消」
- 成功：`data=null`
- 副作用：`status=CANCELLED`、`cancelled_at`、`cancel_by`（`RENTER` / `OWNER` / `ADMIN`）、`cancel_reason`；**删除该订单全部 `order_occupancy` 行**；物品从 `RENTED` 回 `ON_SHELF`
- 错误：`3005`、`3008`（与订单无关的人）、`3001`（已取用或已终结 —— 已取用只能走归还）
- 信誉扣分（确认后取消 −3）**不在本切片**，随切片 5 的 K4 一起落地

### 4.4 立即执行逾期扫描 `POST /api/admin/orders/scan-overdue`（需 ADMIN）

- 入参：无 body
- 成功：

```json
{ "code": 0, "message": "成功", "data": { "updated": 1, "scannedAt": "2026-11-19 20:10:54" } }
```

- 判定条件写死：`status = IN_USE AND end_date < 今天` → `OVERDUE`；返回受影响行数
- 与定时任务（`sys_config['order.scan.cron']`，默认 `0 0 * * * ?`）调用**同一个方法**，不存在两套逻辑
- 幂等：重复点不会重复计数（`OVERDUE` 已不在 `IN_USE` 条件下）
- 错误：`1002` 非管理员

| code | 含义 | 出现处 |
| :-- | :-- | :-- |
| 1001 | 未登录或登录已过期 | 全部接口 |
| 1002 | 无权限访问 | `scan-overdue` 非管理员 |

| 动作 | 状态迁移 | 为什么推迟 |
| :-- | :-- | :-- |
| 归还 `POST /api/orders/{id}/return` | `IN_USE / OVERDUE → COMPLETED` | 归还那一刻必须同时算逾期费、损耗费、生成结算单、释放占用、物品回保养/在架 —— 与 K3 结算同一事务，切开会写两遍 |

| 管理端裁决 | `settlement → ADJUSTED` | 申诉裁定通过时改写 `refund_deposit` 并记 `verdict`，这正是承租方对「损耗认定」的对价手段 |

## 5. 归还、结算与信誉（切片 5，已冻结 2026-11-20）

### 5.0 本切片的公式与口径（**写死，两端都按这里实现，不许各自解释**）

| 项 | 口径 |
| :-- | :-- |
| 归还动作 | 只有**出租方**可以标记归还（线下交接完成），可用状态 `IN_USE / OVERDUE`，目标状态 `COMPLETED` |
| 实际归还日 | 服务端取当天（`LocalDate.now()`），写 `rental_order.actual_return_date` |
| 逾期天数 | `overdueDays = max(0, 实际归还日 − endDate)`，`endDate` 当天归还算 0 |
| 逾期费 | `dailyPrice × [ min(overdueDays, tier1Days) × overdueRate + max(0, overdueDays − tier1Days) × overdueRate × tier2Rate / tier1Rate ]`，其中 `overdueRate` 取**订单快照**，`tier1Days/tier1Rate/tier2Rate` 取 `fee_policy` id=1；结果 2 位四舍五入 |
| 损耗系数 w | `w = termCoef × categoryCoef × returnCoef`，4 位；`termCoef` 按 `rentDays`（≤ `termTier1MaxDays` → `termTier1Coef`，≤ `termTier2MaxDays` → `termTier2Coef`，否则 `termTier3Coef`）；`categoryCoef` 取 `category.loss_coef`；`returnCoef`：`INTACT 1.0 / WORN 1.5 / DAMAGED 3.0` |
| 损耗费 | `lossFee = deposit × w`，2 位四舍五入；`settlement.loss_ratio` 存**本次 w**，不存累计 L |
| 累计损耗 L | `L_after = min(1, L_before + w)`，4 位；写回 `item.loss_value` 并记 `loss_log`（`loss_before / loss_after`） |
| 物品去向 | `L_after ≥ 0.85`（`thresholdRepair`）→ `MAINTAINING` + `action=REPAIR`；`≥ 0.6`（`thresholdMaintain`）→ 回 `ON_SHELF` + `action=MAINTAIN`；否则回 `ON_SHELF` + `NONE`。**归还必须把物品从 `RENTED` 恢复**，否则永久卡死（§2.4 配套义务） |
| 应退押金 | `refundDeposit = max(deposit − overdueFee − lossFee, 0)` |
| 资金流水 | 固定四条：`RENT IN rentAmount`、`OVERDUE IN overdueFee`（>0 才写）、`LOSS IN lossFee`（>0 才写）、`REFUND OUT refundDeposit`，`flow_no` 形如 `F{yyyyMMdd}{6 位}` |
| 结算单状态 | 归还即建单，`status = PENDING_CONFIRM`，`confirm_deadline = 归还时间 + settlement.confirm.hours`（`sys_config`，默认 **48** 小时） |
| 冷静期出口 | 承租方「无异议」→ `SETTLED`；「提异议」→ `DISPUTED` 且同事务建 `appeal(PENDING)`；**超时**由定时任务/管理端按钮自动转 `SETTLED`（`disputed_at` 为空即视为默认接受） |
| 裁决 | 管理员裁定 `ACCEPTED` → 免收损耗费（`lossFee=0`）重算 `refundDeposit`，结算单 `status=ADJUSTED`；裁定 `REJECTED` → 申诉 `REJECTED`，结算单回 `SETTLED` |
| 信誉变动 | 见 §5.9 表；一律走 `credit_log` 幂等键 `uk_credit_biz(user_id, order_id, reason_code)`，`after_score = clamp(before + change, 0, 100)`，正向变动同一自然日累计封顶 **+4** |

### 5.7 申诉裁决 `POST /api/admin/appeals/{id}/verdict`（需 ADMIN）—— **CONTRACT CHANGE（2026-11-20）**

> 变更原因：原设计是 `{accepted: boolean}`——`accepted=true` 被无条件解释成「免损耗费」，
> 但申诉人可能是**出租方**（主张「损耗算少了」），此时「支持」的方向正好相反：
> 系统把损耗费清零，等于让赢了官司的出租方自己承担损失。裁定结果不是一个布尔，而是**四档**。

```json
{
  "verdictType": "PARTIAL",
  "lossFeeOverride": 1.50,
  "creditAdjust": 3,
  "verdict": "双方各有过错，损耗按一半计（≥5 字，≤500 字）"
}
```

| `verdictType` | 含义 | 结算单效果 |
| :-- | :-- | :-- |
| `RENTER_WIN` | 支持承租方（损耗认定不成立） | `lossFee = 0`、结算单 `ADJUSTED` |
| `OWNER_WIN` | 支持出租方（损耗成立） | `lossFee = deposit × lossRatio`（按原损耗率恢复）、`ADJUSTED` |
| `PARTIAL` | 部分支持（由管理员定量） | `lossFee = lossFeeOverride`、`ADJUSTED` |
| `REJECTED` | 驳回异议 | 金额不动、结算单 `SETTLED` |

- 统一重算：`refundDeposit = max(deposit − overdueFee − 新 lossFee, 0)`；申诉单 `status` 记为 `ACCEPTED`（前三种）或 `REJECTED`，并写 `verdict_type / admin_id / verdict_time / verdict`。
- **`lossFeeOverride` 只在 `PARTIAL` 时生效**，必填且 `0 ≤ x ≤ 原 lossFee`，越界 → 2001。
- **`creditAdjust`** 可选，范围 `−50 ~ +50`，作用于**承租方**，落一条 `ADMIN_ADJUST` 信誉流水（`before/after` 由后端 clip 到 `[min, max]`）。留空表示不调整。
- **金额有变化就追加一条冲正流水**：`fee_flow.type = 'ADJUST'`，`direction = delta > 0 ? 'OUT' : 'IN'`，`amount = |delta|`，remark 写「损耗费 a → b，应退 c → d」。历史 4 条流水**永不修改只追加**，所以结算单与流水始终能对上。
- **损耗回滚按比例**：`lossFee` 调低时，从 `loss_log.weight` 按 `1 − 新/原` 的比例回滚 `item.loss_value`；物品原为 `MAINTAINING` 且新损耗降到 `loss_policy.threshold_repair` 以下则恢复 `ON_SHELF`。`RENTER_WIN` 还会把承租方的 `DAMAGE` 扣分用 `ADMIN_ADJUST` 反向回滚（不改历史行）。
- 申诉不是 `PENDING` → 3009；申诉不存在 → 3011；`verdictType` 不在四档内 → 2001。

### 5.8 立即执行结算冷静期扫描 `POST /api/admin/settlements/scan-confirm`（需 ADMIN）

### 5.11 承租方发起归还申请 `POST /api/orders/{id}/return/request`（需登录，仅承租方）

**为什么有这一步（写进论文的动机）**：只有出租方能点「确认归还」的话，会出现单边死角 —— 承租方已经把物品还回去了，出租方拖着不点，订单永远停在 `IN_USE/OVERDUE`，占用不释放、结算不生成、也没有申诉入口（申诉只能从结算单发起）。所以补一条"承租方先申报、出租方验收、超时兜底"的对称路径。

请求体（与 §5.1 同结构）：

```json
{ "returnState": "INTACT | WORN | DAMAGED", "remark": "可选，≤255 字" }
```

**这一步不改订单状态**（仍是 `IN_USE / OVERDUE`，物品还在承租方手上），只写三个字段：

| 字段 | 含义 |
| :-- | :-- |
| `rental_order.return_requested_at` | 承租方申报时间 |
| `rental_order.return_requested_by` | 固定 `RENTER`（留列便于将来扩展） |
| `rental_order.return_requested_state` | 承租方申报的归还状态 |

之后两条出口，**谁先到谁生效**：

| 出口 | 行为 |
| :-- | :-- |
| 出租方验收（§5.1） | 以出租方验收的状态为准结算；申报时间戳保留作为"谁先说还了"的证据 |
| 超过 `order.return.confirm.hours`（默认 24h）出租方仍未确认 | 扫描任务 / 管理端 §5.12 按**承租方申报的状态**自动结算，`settlement.remark` 写「出租方超时未确认归还，按承租方申报自动结算」 |

错误码：非承租方 → 3008；状态不是 `IN_USE/OVERDUE` → 3001；已发起过（`return_requested_at` 非空）→ 3001「已提交过归还申请（时间），请等待出租方确认」；`returnState` 非法 → 2001；已存在结算单 → 4003。

窗口值来自 `sys_config['order.return.confirm.hours']`（种子 24），**前端不要自己算截止时间**。

### 5.12 立即执行归还申请超时扫描 `POST /api/admin/orders/scan-return`（需 ADMIN）

与定时任务（`settlement.scan.cron`，每小时第 5 分）调的是同一个方法 `settlementService.scanReturnTimeout()`：

```json
{ "updated": 1, "scannedAt": "2026-11-20 20:30:00" }
```

每单一个独立事务：一单失败只记日志并跳过，不影响其他单，也不会留下"订单完成了但没结算"的半成品。幂等（已结算的订单不再被选中）。

## 6. 推荐、看板与参数配置（切片 6，已冻结 2026-11-23）

### 6.0 口径（写死，两端按此实现）

| 项 | 口径 |
| :-- | :-- |
| 打分公式 | `score = wCf × cf + wContent × content + wHeat × heat`，三个权重与 `top_n`、衰减半衰期、热度窗口**全部来自 `sys_config`**（`recommend.w.cf` 0.6 / `recommend.w.content` 0.3 / `recommend.w.heat` 0.1 / `recommend.decay.half_life` 30 / `recommend.heat.window` 30 / `recommend.top_n` 10），代码里禁止写 0.6/0.3/0.1 字面量 |
| `cf`（协同过滤） | 以订单为边建 `(user, item)` 共现：`cf(i) = Σ_{j ∈ 我租过的} co(i,j) × 0.5^(距今小时/半衰期天数)`，结果对当前候选集按最大值归一化到 `[0,1]`；`co` 为「同时租过 i 与 j 的用户数」 |
| `content`（内容） | 有历史时：`0.5×同二级类目 + 0.3×同父类目 + 0.2×(1 − |p_i − p̄| / max(p_i, p̄))`（`p̄` 为我租过物品的均价）；无历史时用「同小区」替代 |
| `heat`（热度） | `rent_count + 0.2 × view_count`，按当前候选集最大值归一化到 `[0,1]`（本课题不做时间窗口内的 UV 统计，窗口参数保留但按累计值实现，注明为简化） |
| 候选范围 | 只取 `status = 'ON_SHELF'`；**排除自己发布的**；**排除我正在租（`PENDING/CONFIRMED/IN_USE/OVERDUE`）的物品**；候选上限 200 条（超出按 `rent_count` 取前 200 再打分） |
| 冷启动 | 当前用户没有任何订单 → 走「同小区 → 同片区 → 热度」，`coldStart = true`；匿名访问同此逻辑（`coldStart = true`） |
| `reason` | **由后端生成**（前端只渲染），`reasonCode` 四选 `CF` / `CONTENT` / `HEAT` / `COLD_START`，文案模板见 §6.1 |
| 排序 | `score` 降序；分数相同按 `rent_count` 降序、`id` 降序，保证结果稳定可复现 |
| 性能目标 | 单次 ≤ 500ms（**目标值**，候选上限 200 条，打分在内存完成，只允许 2–3 条 SQL） |


- 字段白名单以外 → 2001；类型不对 → 2001；
- **区间校验**由后端做（不能只靠 DB 的 CHECK，否则前端拿到的是 `SQLException`）：例如 `thresholdRepair > thresholdMaintain`、`minScore ≤ maxScore`、`overdueRateMin ≤ overdueRateMax`，越界 → 2001 并指明字段；
- 写成功返回最新对象（同 §6.4 的单表结构）。**立即生效**：后端每次用到参数都读库，没有本地缓存。

### 6.6 修改单个系统参数 `PUT /api/admin/config/sys/{key}`（需 ADMIN）

```json
{ "value": "0.5" }
```

- 只允许修改**已存在的 key**（新增参数走 SQL + 迁移，避免管理端随手造出代码不认识的键）→ 不存在 2001「未知参数」；
- 按 `valueType` 校验：`INT` 整数、`DECIMAL` 数字、`BOOLEAN` `true/false/1/0`、`CRON` 非空且含 5–6 段空格分隔；不合法 → 2001；
- 返回 `{ configKey, configValue, updateTime }`。同样立即生效。

### 6.7 本切片用到的错误码

| code | message | 出现场景 |
| :-- | :-- | :-- |
| 1001 | 未登录或登录已过期 | 管理端全部接口 |
| 1002 | 无权限访问 | 非 ADMIN 调 `/api/admin/**` |
| 2001 | 参数不合法 | `limit`/`days` 越界、策略字段越界或类型错、未知参数 key |
| 5000 | 系统繁忙，请稍后重试 | 参数表缺 `id = 1`、统计 SQL 异常 |

## 7. 站内消息（2026-11-23 补，承接需求 §4 的消息提醒）

> 这一节补的不是新需求：说明书与需求总结 §4 一直有「消息提醒」，早期切片为了不打断主链只建了 `message` 表，接口留到现在补。
> 接口总数 44 → 48。

### 7.0 口径

| 项 | 约定 |
| :-- | :-- |
| 谁能看 | 只能看自己的消息。`userId` 一律从令牌取，不接受请求参数 |
| `type` | `ORDER` 订单 / `CREDIT` 信誉 / `MAINTAIN` 检修 / `SYSTEM` 系统（决定标签颜色分组） |
| `bizType` | `ORDER` / `SETTLEMENT` / `ITEM`（决定点击跳哪一页），**与 `type` 是两套含义，别合并** |
| 已读 | `read` 布尔；单条标记**幂等**，重复标记不报错、不重复扣减 |
| 写入时机 | 只在业务状态**变更成功之后**写；`notify` 内部吞异常，消息发不出去不影响主流程 |
| 实时性 | 不做推送（无 WebSocket），靠进入页面/切换路由时拉未读数 |
| 时间 | `createdAt` 形如 `2026-11-23 19:41:02` |

### 7.1 `GET /api/messages`（需登录）

查询参数：`pageNum`（默认 1）、`pageSize`（默认 10，上限 100）、`unreadOnly`（`true` 只看未读）。

```json
{ "code": 0, "message": "成功",
  "data": { "list": [ { "id": "31", "type": "ORDER", "typeLabel": "订单",
                        "title": "有新的租赁申请",
                        "content": "「R202611230001」申请在 2027-02-21 至 2027-02-23 租用你的物品，请及时确认。",
                        "bizType": "ORDER", "bizId": "1684", "read": false,
                        "createdAt": "2026-11-23 19:41:02" } ],
            "total": 3, "pageNum": 1, "pageSize": 10 } }
```

### 7.2 `GET /api/messages/unread-count`（需登录）

```json
{ "code": 0, "message": "成功", "data": { "count": 2 } }
```

单独一个接口的原因：顶栏铃铛每个页面都要显示未读数，而列表只有消息页才查 —— 两个查询的频率差两个数量级，合成一个接口会让首页多传一整页数据。

### 7.3 `POST /api/messages/{id}/read`（需登录）

无请求体，返回 `{"code":0,"message":"成功","data":null}`。幂等：已读再点仍返回 0。
错误：`2001 消息不存在`、`3008 只能操作自己的消息`。

### 7.4 `POST /api/messages/read-all`（需登录）

无请求体，`data` 为本次实际更新条数（`0` 表示本来就没有未读）。

| 错误码 | 含义 |
| :-- | :-- |
| 1001 | 未登录 |
| 2001 | 消息不存在（仅 7.3 单条已读） |
| 3008 | 只能操作自己的消息 |
