## 1. K2 并发证据（最关键的一条）

### 1.1 用例本身

`backend/src/test/java/com/duyikang/rental/module/order/OrderConcurrencyTest.java`

- **场景**：50 个线程同时给「同一物品、同一时段」下单；物品 4（李娜的在架小说），承租人张伟；时段 = `今天 + 40 天` 起 3 天。
- **为什么单独一个类且不加 `@Transactional`**：并发线程各自开自己的事务，外层测试事务回滚不了它们。所以这里用**真实提交**，再由 `@AfterEach cleanUp()` 按「执行前的最大订单 id 之后」删除本次产生的订单与占用 —— 不碰种子数据，也不碰用户手工下的单。
- **三闸齐发**：`CountDownLatch ready(50)` 等所有线程就位 → `fire(1)` 同时放行 → `done(50)` 等全部结束。这是并发测试的标准写法，缺了 `ready` 就变成"顺序压测"，测不出竞态。

### 1.2 断言口径（这就是"零放行"的定义）

| 断言 | 期望 | 为什么是这个数 |
| :-- | :-- | :-- |
| 成功数 | **恰好 1** | K2 的全部意义 |
| `4090` 数 | **恰好 49** | 其余全部是"时段已被占用"，业务上可解释的拒绝 |
| `5003`（锁失败）数 | **0** | 抢锁超时必须翻译成 4090（规则 §8.3），漏成 5003 说明错误码口径破了 |
| `5000`（系统异常）数 | **0** | 任何非业务异常的兜底码，出现即 bug |
| 占用行数 | **= 订单天数（3）且日期互不重复** | 逐日展开正确、唯一索引兜底没白设 |

### 1.4 三层防线分别在哪儿（答辩必问）

| 层 | 代码位置 | 作用 | 单独失效会怎样 |
| :-- | :-- | :-- | :-- |
| ① 应用层预检 | `OrderServiceImpl#create` → 先查 `order_occupancy` 是否已有交集 | 把绝大多数冲突挡在事务之外，省一次锁与一次回滚 | 只是性能问题：冲突请求变多，但不会超卖 |
| ② Redis 分布式锁 | `RedisLock#tryLock("lock:item:{id}", uuid, 10s)`，50ms×10 次重试 | 让同物品的下单**串行化**，避免大量请求一起去撞唯一索引 | 仍不超卖，但并发时 4090 会集中爆发（靠第三层兜底） |
| ③ 唯一索引 | `uk_occupancy(item_id, occupy_date)` + 逐日展开 `INSERT` | **正确性的最终保证**——数据库层面不可能出现两条同物品同日占用 | 会超卖，此时任何应用层逻辑都救不回来 |

关键细节（规则 §8.3 的三条前提，别在论文里说反）：
1. **逐日展开**：订单 `[start, end)` 半开区间，跨 N 天就插 N 行。一单一行的话唯一索引永远不触发，第三层等于不存在。
2. **锁在事务外、释放在提交后**：加锁方法不标 `@Transactional`，真正写库在 `OrderTxService#createInTx`；锁若在事务内 `finally` 释放，会出现"锁已放、数据未提交"的窗口。
3. **预检不可信**：预检只是优化，判断"有没有冲突"的最终决定权在唯一索引。

| 用例 | 期望 |
| :-- | :-- |
| 按时归还 | 结算单 `PENDING_CONFIRM`、`overdueFee = 0`、`refund = 押金 − 损耗费`、占用清零、订单 `COMPLETED` |

| 取消解冻 | `PENDING` 单取消 | `frozen −160.00`、`cash +160.00`，`ORDER_RELEASE` 一条分录 |
| 结算（按时、完好） | 归还 `INTACT` | 承租方 `frozen −160`、`cash +100`；出租方 `cash +60`；平台 0；`SETTLE` 分录守恒 |
| 结算（逾期 + 损耗） | 归还 `WORN` 且逾期 5 天 | 承租方拿回「押金 − 逾期费 − 损耗费」、出租方拿「租金 + 逾期费」、平台拿损耗费；三方总资产前后相等 |
| 裁决改判 | `RENTER_WIN` 免掉损耗费 | 承租方 `+delta`、平台 `−delta`、`VERDICT` 分录守恒；`fee_flow` 同时多一条 `ADJUST` |
| 幂等 | 同一结算触发两次 | 第二次不新增分录、余额不再变（`uk_entry_biz` 兜住） |
| 管理端调整 | 给用户 `+100.00` | 用户 `cash +100`、平台 `−100`、`ADMIN_ADJUST` 分录；扣成负数 → 4005 |
