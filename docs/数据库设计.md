## 0. 建表前先问自己的 11 个问题

这份文档不是"把字段列出来"，而是先回答清楚**为什么是这些表、为什么是这些列、为什么这么建索引**。以下 11 个问题必须先有答案，才允许写 DDL。

| # | 问题 | 本项目的答案（结论） |
| :-- | :-- | :-- |
| Q1 | 这个项目最容易被并发打穿的地方是哪里？ | **K2 时段冲突**。所以必须有一张**按天粒度**的占用表 + 唯一索引，而不是靠"下单前查一下"。 |
| Q2 | 如果把 K2 的锁、预检全删掉，数据库还能不能防超卖？ | 能 —— 只要 `order_occupancy` 逐日展开且 `uk_occupancy(item_id, occupy_date)` 存在。这是"数据库最后一层防线"的验收标准。 |
| Q3 | 钱会不会算错？ | 所有金额 `DECIMAL(10,2)`，全库无 float/double（A9 断言）；租金、押金、逾期费率在下单时**快照**进订单，改价不影响历史。 |
| Q4 | 状态会不会"非法跳转"？ | 六状态由应用层状态机守卫；数据库再用 CHECK 把"自租""日期倒挂""天数≤0"这类**静态不可能**的状态挡掉。 |
| Q5 | 一次操作会不会重复记账？ | 三个幂等键：`uk_settle_order`（一单一结算）、`uk_credit_biz`（同一订单同一原因只加一次分）、`uk_flow_no`（流水号唯一）。 |
| Q6 | 出租方 / 承租方要不要两张用户表？ | **不要**。K1 要求 `user` 只存账号，双边角色由 `rental_order.owner_id` / `renter_id` 表达。`item.owner_id` 与 `rental_order.owner_id` 语义不同，不可互替。 |
| Q7 | 哪些数据不许物理删除？ | 订单、结算、流水、信誉、损耗、占用 —— 全是**审计/对账证据**，只允许状态流转；只有 `user`/`item`/`category`/`message` 带 `deleted` 逻辑删除。 |
| Q8 | 索引会不会建多？ | 每个索引都要能对上一条真实查询（§5 的对照表）。没对上的不建。写多读少的日志表只留"按时间倒序"和"按订单反查"两个。 |
| Q9 | 物品图片怎么存？ | 库里只存相对路径，`item_image` 一对多 + `item.cover_url` 冗余首图（列表页零 join）。不存二进制、不存外链（§3.4.1）。"图片≥1"是跨行约束，只能 Service 校验 |
| Q10 | 规则参数放代码还是放库？ | 放库。三类同构参数用**结构化单行表**，零散异构参数用**键值表**（§3.7 说明为什么两种都用）。 |
| Q11 | 建完怎么证明对了？ | 跑 `03-verify.sql` 的 17 条断言 + 11 条负向测试（故意插非法数据，必须报错）。**没跑过就不算建完。** |

## 2. 关系图（逻辑关系，**物理上不建外键**）

```
                        ┌────────┐        ┌──────────┐
                        │  role  │───┐    │ category │ (自关联 parent_id，两级)
                        └────────┘   │    └────┬─────┘
                                     │         │ category_id
                              ┌──────┴───┐  ┌──┴────┐
                              │ user_role│  │ item  │ owner_id ──┐
                              └──────┬───┘  └───┬───┘            │
                                     │          │ item_id        │
                                     │          ├──────► item_image (1 : N)
                                     │          │ item_id        │
┌────────┐  renter_id / owner_id     │  ┌───────┴────────┐       │
│  user  │───────────────────────────┴──┤ rental_order   │◄──────┘
└───┬────┘                              └───┬───┬────┬───┘
    │ user_id                               │   │    │ order_id
    ├──────────────► credit_log ◄───────────┘   │    └──► order_occupancy (item_id, occupy_date)
    ├──────────────► message                    │
    │                                           ├──► settlement ──► fee_flow
    │                                           ├──► loss_log
    │                                           └──► appeal
    └──────────────► item (owner_id)

配置表（无外键，全表单行 id=1 / 键值）：credit_policy、fee_policy、loss_policy、sys_config

社区字典（同样不建外键，整数等值引用）：community ← user.community_id（可空）/ item.community_id（必填）
```

**为什么不建物理外键**（PROJECT_RULES.md §5）：
1. 毕设数据靠脚本初始化与重置，外键会让 `02-data.sql` 的插入顺序变得脆弱；
2. 逻辑删除（`deleted=1`）与外键约束天然冲突 —— 父行"删"了但物理还在；
3. 关联完整性由应用层事务 + 唯一索引保证，且唯一索引提供的防护强于外键（外键不防重复，唯一索引防重复）。

**代价**也写明：可能出现"孤儿行"（例如订单引用了不存在的 item_id）。所以 `03-verify.sql` 里保留跨表一致性断言（A2–A4），并在服务层禁止直接删主表数据。

## 3. 逐表字段设计

> 只解释"**为什么需要这一列**"，不重复 DDL 的类型细节（DDL 里有 COMMENT）。表结构以 `backend/sql/01-schema.sql` 为准。

### 3.1 `user` 用户账号表

| 字段 | 类型 | 为什么需要它 |
| :-- | :-- | :-- |
| `id` | BIGINT UNSIGNED AI | 主键；前端按字符串传输（Long 精度问题） |
| `nickname` | VARCHAR(32) | 展示名，不唯一（同名真实存在） |
| `phone` | VARCHAR(20) | **登录名**，`uk_user_phone` 唯一 |
| `password_hash` | VARCHAR(100) | BCrypt，恒 60 位；**绝不存明文** |
| `avatar_url` | VARCHAR(255) | 头像 |
| `community_id` | BIGINT UNSIGNED | 指向 `community` 字典；**可空**（不填 = 不参与"同小区优先"，注册流程不卡壳）。为什么不存字符串：`阳光花园` / `阳光花园小区` / `阳光花园东区` 是同一个小区，字符串相等比较会把邻居判成陌生人 |
| `credit_score` | INT | 信誉分；`CHECK 0..100` 是硬边界 |
| `status` | VARCHAR(16) | `NORMAL` / `DISABLED`（禁用后登录返回 1006） |
| `last_login_at` | DATETIME | 运营观察、答辩演示"活跃度" |
| `created_at` / `update_time` | DATETIME | 审计 |
| `deleted` | TINYINT | 逻辑删除（MyBatis-Plus `@TableLogic`） |

**刻意不加的列**：`is_owner` / `is_renter`（违反 K1）、`balance`（不做真实支付）、`real_name`（不做实名认证）。

### 3.2 `role` / `user_role`

- `role.code` 唯一，取值 `USER` / `ADMIN`；Spring Security 侧映射 `ROLE_USER` / `ROLE_ADMIN`。
- `user_role` 用 `uk_user_role(user_id, role_id)` 防重复授予。
- 为什么不做"权限表"（`permission` / `role_permission`）：本课题只有两种角色、权限差别是"能不能进 `/api/admin/**`"，用一个角色码足以表达；加权限表是**过度设计**（§10 灰区裁决 Q2：不在主链上）。

### 3.2.1 `community` 社区字典（`user` / `item` 共用）

| 字段 | 为什么需要它 |
| :-- | :-- |
| `name` + `district` + `city` | 三列拼出唯一性：`uk_community_city_district_name`。只写 name 唯一会把"城东的阳光花园"和"城西的阳光花园"判重 |
| `district` | 列表页与推荐的**第二排序档**「同片区」靠它等值比较，不需要任何距离计算 |
| `alias` | 逗号分隔的别名（注册时用户打字用的旧名/俗称），**只给管理端搜索用，不参与匹配**。匹配一律走 `community_id`，别名再多也不会让排序失真 |
| `enabled` | 停用小区时**只改状态不删行**（`ck_community_enabled` 限 0/1）。删行会让历史 `user.community_id` / `item.community_id` 变成悬空引用 |
| `sort_no` | 下拉框顺序（城东的排前面），与 `enabled` 组成 `idx_community_enabled(enabled, sort_no)`，一个索引同时服务过滤与排序 |

**为什么字典化，而不是继续存字符串**：字符串相等无法容纳别名；改名要 `UPDATE` 全表；统计"某小区有多少件物品"要扫字符串。字典化后这三件事分别退化为整数比较、改一行、走 `idx_item_community`。

**为什么仍然不做地图**：需求总结 §10 明确"地图选址、距离排序 → 不做"。本表只提供"同小区 / 同片区 / 其他"三档，答辩口径是"用整数等值替代地理计算，避免引入坐标与距离模型的额外复杂度"；将来若要按距离排序，给本表加 `lat` / `lng` + haversine 排序键即可，引用关系不用动。

### 3.3 `category` 类目

| 字段 | 为什么需要它 |
| :-- | :-- |
| `parent_id` + `level` | 两级树；`level` 是冗余列，避免每次递归判断层级 |
| `loss_coef` | 类目损耗系数（电子 0.03 / 帐篷 0.025 / 工具 0.015 / 图书 0.008），**放在类目上而不是配置表**：它是"随类目走的属性"，不是全局阈值 |
| `uk_category_parent_name` | 同级下重名会让人选错类目 |
| 种子构成（2026-11-18 扩充） | **7 个一级 × 21 个二级 = 28 行**：电子数码（相机/耳机/投影仪）、户外露营（帐篷/睡袋/折叠桌椅/烧烤炉）、工具五金（电钻/梯子/手动工具套装）、图书文具（小说/教材教辅/桌游棋牌）、家居生活（宠物/厨房小电/清洁电器）、运动健身（瑜伽垫/羽毛球拍/健身器材）、母婴玩具（儿童玩具/婴儿推车）。二级 `loss_coef` 按"越精密越易损"取经验值：相机 0.035 最高，教材教辅 0.005 最低 |

### 3.4 `item` 物品

| 字段 | 为什么需要它 |
| :-- | :-- |
| `owner_id` | 归属人。**注意与 `rental_order.owner_id` 语义不同**（后者是"这笔订单的出租方"，下单时冗余快照） |
| `community_id` | **必填**：物品所在小区，列表页第一排序档「同小区」的判定列。存 id 而非小区名，改名时不必动 7 件物品 |
| `cover_url` | 封面图 = `item_image` 里 id 最小的那张。**冗余一份**：列表页一次查询就出图，不必为 20 条数据做 20 次子查询或 join 去重 |
| 三档价格 `daily_price` / `deposit` / `overdue_rate` | 下单时会被**快照**进订单；`overdue_rate` 必须落在 `fee_policy` 的 `[min,max]` 内（应用层校验，配置是数据，无法写成 CHECK） |
| `loss_value` | 累计损耗值 L ∈ [0,1]，达到阈值触发保养/检修 |
| `status` | 六态：`PENDING` 待审 / `ON_SHELF` 在架 / `OFF_SHELF` 下架 / `RENTED` 租出中 / `MAINTAINING` 检修中 / `REJECTED` 驳回 |
| `rent_count` / `view_count` | 热度特征。**冗余计数**而非 `COUNT(*)`：推荐要对全量物品算热度，实时聚合会拖慢列表 |
| `audit_*` | 审核留痕（谁、何时、什么意见），管理端要能追溯 |

### 3.4.1 `item_image` 物品图片（1 : N）

| 字段 | 为什么需要它 |
| :-- | :-- |
| `item_id` | 归属物品；`idx_item_image_item(item_id, id)` 让详情页 `WHERE item_id=? ORDER BY id` 走索引顺序读 |
| `url` | **只存相对路径**（`/uploads/202611/xxx.jpg`），不存二进制、不存外链。理由：图片走本地磁盘 + 静态资源映射（需求总结 §2.3），库里存路径才能换存储方案而不动数据 |
| `created_at` | 排障：可判断图片是否在审核后被替换 |
| `uk_item_image(item_id, url)` | 同一物品重复提交同一张图会被 1062 拦住——前端重复点"上传"是很常见的 bug，让数据库兜住 |

**为什么不做 `sort_no`**：需求总结 §10 灰区把"多图排序、图片裁剪"裁定为 **P2 不做**。上传顺序即展示顺序，用自增 `id` 排序就够；加排序字段会连带出拖拽交互、批量重排接口、排序值冲突处理，全是 P2 成本。

**为什么 `cover_url` 和 `item_image` 同时存在（看起来冗余）**：
- 列表页（P0 主链，最高频）只 `SELECT` 一行一张图，不 join、不做 `GROUP BY MIN(id)`；
- 代价是"改封面/删首图"时要同事务更新两处 —— 这条写进 Service 实现要求，并 **A16 断言**兜底（封面必须等于 id 最小的图，否则报 FAIL）。

**约束强度说明（要能接住答辩提问）**：MySQL 无法用 CHECK 表达"每件物品至少 1 张图"（跨行约束），这条**只能由 Service 校验**（发布接口：图片列表为空 → `2001`）。数据库能给的是"有图就不许重复"和"封面必须对得上"。这正是 A15 只能做**数据巡检**、不能做**强约束**的原因。

### 3.5 `rental_order` 订单

| 字段 | 为什么需要它 |
| :-- | :-- |
| `order_no` | 业务单号，`uk_order_no`；对外交流用单号，不暴露自增 id |
| `owner_id` + `renter_id` | **双边角色**，K1 的落点；`CHECK owner_id <> renter_id` 是自租的第二道防线（第一道在 Service，返回 3006） |
| `start_date` / `end_date` | 半开区间 `[start, end)`。10-01~10-04 表示占用 3 天，`end_date` 是"应当归还的那天"，不计费 |
| `rent_days` | 冗余列 = `DATEDIFF(end_date, start_date)`；存下来才能用 `CHECK rent_days > 0`，也避免每次查询都算 |
| `daily_price` / `deposit` / `overdue_rate` | **价格快照**。出租方事后改价不得影响历史订单（否则结算不可对账） |
| `rent_amount` | 下单时算好的租金；`A6` 断言它恒等于 `daily_price × rent_days` |
| `overdue_days` / `actual_return_date` | 逾期计费依据 |
| `status` | 六状态机，单向，不回退 |
| `confirmed_at` / `in_use_at` / `completed_at` / `cancelled_at` | 状态流转时间戳，答辩时可直接展示"这一单经历了什么" |
| `cancel_reason` / `cancel_by` | 谁取消、为什么取消；`cancel_by ∈ {RENTER, OWNER, ADMIN}` 决定是否扣分 |
| `return_requested_at` / `return_requested_by` / `return_requested_state` | **归还申请（2026-11-20 新增，方案 B）**：承租方点「我已归还」时只写这三列，**订单状态不变**（物品还在承租方手上，占用不能提前释放）。`return_requested_state ∈ {INTACT, WORN, DAMAGED}`；出租方在 `order.return.confirm.hours`（默认 24h）内验收确认则以其验收成色结算，超时则按申报成色自动结算。`idx_order_return_request(status, return_requested_at)` 支撑超时扫描；`A24` 断言「PENDING/CONFIRMED 不得有申请时间、有申请时间必须有合法申报成色」 |

**为什么用三列而不是加第七个状态**：状态机扩态等于改论文立论（六状态是需求总结 §6 的口径），而"已申报待验收"本质是 `IN_USE` 上的一个**子情形**，用时间戳表达既不动状态机，也不影响占用释放规则（占用只在 `COMPLETED / CANCELLED` 消失）。

**刻意不加**：`settled_amount`（在 `settlement` 里，避免双写）、`status_log` 表（见 §7 取舍 5）。

### 3.6 `order_occupancy` 时段占用 ★ K2 核心

| 字段 | 为什么需要它 |
| :-- | :-- |
| `item_id` + `occupy_date` | **唯一索引 `uk_occupancy`** 的两列。一条记录 = "某物品的某一天被占了" |
| `order_id` | 释放占用时按订单 `DELETE`；也用于"这笔订单占了哪几天" |
| `created_at` | 排障：什么时候写入的 |

**逐日展开是这条防线的命门**：

```
订单 11-20 ~ 11-23  →  INSERT 3 行：
  (item, '2026-11-20'), (item, '2026-11-21'), (item, '2026-11-22')
```

如果图省事改成"一单一行存 start/end"，任意两笔订单的 `(item_id, start_date)` 天然不同 —— **唯一索引永远不会冲突，K2 第三层防线直接失效**。这是 AI 最可能犯的错，已写进 `PROJECT_RULES.md` §0 铁律 3 与 §8.3 前提 1。

### 3.7 结算与配置

**`settlement`**：一单一结算（`uk_settle_order`）+ 结算单号唯一（`uk_settle_no`）双幂等。金额列 `rent_amount` / `deposit_amount` / `overdue_fee` / `loss_fee` / `refund_deposit`，`A5` 断言 `refund_deposit = GREATEST(deposit_amount − overdue_fee − loss_fee, 0)`。
`loss_ratio` 存**本次**损耗值 `w`（不是累计 `L`），因为损耗费 = 押金 × 本次损耗值；累计 `L` 落在 `item.loss_value` 与 `loss_log.loss_after` 上。

**结算冷静期（2026-11-20 扩表）**：`status` 由两态扩为四态 `PENDING_CONFIRM / SETTLED / DISPUTED / ADJUSTED`
（对应承租方"还没表态 / 点了无异议 / 提了异议 / 管理员裁决调整过"），并新增三列：

| 列 | 类型 | 作用 |
| :-- | :-- | :-- |
| `confirm_deadline` | DATETIME | 冷静期截止（归还时间 + `sys_config['settlement.confirm.hours']`，默认 48 小时），`A21` 断言 `PENDING_CONFIRM`/`DISPUTED` 必有值 |
| `confirmed_at` | DATETIME | 承租方点什么的时间（确认或提异议） |
| `disputed_at` | DATETIME | 提异议时间 |

`settled_at` 由建单即写改为**结清才写**（`SETTLED` / `ADJUSTED`），`A21` 断言这两态必非空。
为什么要这一层：损耗是出租方点"归还"那一刻单方面认定的，承租方没有对价手段就等于"卖家自己判自己赢"。
冷静期给了承租方 48 小时窗口：点无异议 → `SETTLED`；提异议 → `DISPUTED` 并生成 `appeal`；
超时未表态由 `SettlementScanJob` 自动确认（演示时管理端有「立即执行冷静期扫描」按钮）。
没有采用"承租方点归还 + 出租方确认"的方案，因为那会把六状态机扩成七态，动摇论文立论。

**申诉裁决为什么用四档枚举而不是布尔（2026-11-20）**：`appeal` 新增 `verdict_type VARCHAR(24)`
（`RENTER_WIN` / `OWNER_WIN` / `PARTIAL` / `REJECTED`）。原来的 `verdict` 只有一句说明文字、
`accepted` 是布尔，而 `accepted = true` 被无条件解释成「损耗费归零」——可申诉人是**双方**：
承租方申诉是「这笔损耗不该算」，出租方申诉是「损耗算少了」。同一个 `true` 对两者方向相反，
于是出租方胜诉反而自己承担损失。所以裁定结果必须是四档，金额改动用 `ADJUST` 流水冲正、
物品损耗按比例回滚、信誉调整走 `ADMIN_ADJUST`（历史 `credit_log` 行不回改）。

**`fee_flow`**：把一笔结算拆成可对账的条目（租金/押金/逾期费/损耗费/退款），`direction ∈ {IN, OUT}`。不做真实支付，但账面必须能对上 —— 论文里"结算零人工"的证据就是它。

**只追加不改写**：管理员裁决改了金额时，新增一条 `type = 'ADJUST'` 的冲正流水（应退增加记 `OUT`、减少记 `IN`），历史四条流水原样保留。这样「结算单金额 = 流水净额」在任何时刻都成立，答辩被问"钱对不上怎么办"时有据可查。

**配置为什么用两种形态**：

| 形态 | 表 | 理由 |
| :-- | :-- | :-- |
| 结构化单行表 | `credit_policy` / `fee_policy` / `loss_policy` | 参数同构且**有确切类型**（0.5 是 DECIMAL 不是字符串）。改一个阈值 = `UPDATE ... SET overdue_tier1_rate = 0.6 WHERE id = 1`，`PolicyLoader` 一条 `SELECT ... WHERE id = 1` 就加载完 |
| 键值表 | `sys_config` | 参数异构零散（权重、半衰期、cron 表达式），加一个参数不必改表结构 |

单行表的硬约束：**`id` 固定为 1**，禁止插第二行（`A14` 断言）。所有策略表都带 `CHECK` 保证区间自洽（如 `threshold_repair > threshold_maintain`），防止管理员在页面上填出"检修阈值低于保养阈值"。

### 3.8 `account` / `account_entry` 账户与复式分录（2026-11-23 增）

**为什么需要这两张表**

`fee_flow` 记的是「这单产生了哪些费用」，是**业务视角**；它答不了「钱现在在谁手上」。补账务后，两个问题各有归属：

| 问题 | 由谁回答 |
| :-- | :-- |
| 这单收了我多少钱、退了多少 | `settlement` + `fee_flow` |
| 我的钱包还剩多少、这 60 块去哪了 | `account` + `account_entry` |

**`account`（账户，一行一个主体）**

| 字段 | 类型 | 说明 |
| :-- | :-- | :-- |
| `id` | BIGINT UNSIGNED AI | |
| `owner_type` | VARCHAR(16) | `USER` / `EXTERNAL` |
| `owner_id` | BIGINT UNSIGNED | 用户 id；平台账户固定 `0` |
| `cash_balance` | DECIMAL(12,2) | 可用余额 |
| `frozen_balance` | DECIMAL(12,2) | 冻结余额（在途订单占用） |
| `version` | INT | 乐观锁版本号，每次改动 +1 |
| `created_at` / `update_time` | DATETIME | |

约束：`uk_account(owner_type, owner_id)`（一个主体一个账户）、`ck_account_balances(cash_balance >= 0 AND frozen_balance >= 0)`。

**`account_entry`（分录，只追加不修改）**

| 字段 | 类型 | 说明 |
| :-- | :-- | :-- |
| `id` | BIGINT UNSIGNED AI | |
| `entry_no` | VARCHAR(32) | `E` + `yyyyMMdd` + 当日 4 位序号 |
| `biz_type` | VARCHAR(24) | `RECHARGE` / `ORDER_FREEZE` / `ORDER_RELEASE` / `SETTLE` / `VERDICT` / `ADMIN_ADJUST` |
| `biz_id` | BIGINT UNSIGNED | 业务单据 id（订单 / 结算单 / 申诉） |
| `action` | VARCHAR(24) | 同一业务内的细分动作：`FREEZE` / `RELEASE` / `RENT` / `OVERDUE` / `LOSS` / `REFUND` / `ADJUST` / `RECHARGE` |
| `order_id` | BIGINT UNSIGNED NULL | 关联订单（便于按单查账） |
| `from_account_id` | BIGINT UNSIGNED | 出账账户 |
| `to_account_id` | BIGINT UNSIGNED | 入账账户 |
| `amount` | DECIMAL(12,2) | **正数**，方向由 from/to 表达 |
| `from_cash_after` / `from_frozen_after` | DECIMAL(12,2) | 出账账户记账后余额（审计用；出账账户非用户时可为 NULL） |
| `to_cash_after` / `to_frozen_after` | DECIMAL(12,2) | 入账账户记账后余额 |
| `remark` | VARCHAR(255) | 人话说明 |
| `created_at` | DATETIME | |

约束：`uk_entry_no`、`uk_entry_biz(biz_type, biz_id, action, from_account_id, to_account_id)`（**幂等**：同一业务的同一动作只能入账一次）、`ck_entry_amount(amount > 0)`、`ck_entry_accounts(from_account_id <> to_account_id)`。

**为什么用 from/to 两列而不是一列带符号**：一列带符号时，"这笔钱从哪来"要靠猜；两列直接把「谁出谁进」写进行里，`SUM` 一拉就能验证守恒，对账 SQL 也简单。

**为什么不加物理外键**：与全库一致（见 §2）；账户 id 由应用层保证，`03-verify` 里用断言兜（新增 A26 账户指向合法用户、A27 逐业务号守恒）。
**种子**：`EXTERNAL` 账户一行（`owner_id = 0`，`cash_balance = -4000.00`，表示已从外部净流入的资金）；四个种子用户各一行，`cash_balance = 1000.00`、`frozen_balance = 0.00`，并各写一条 `biz_type = 'RECHARGE'`、`remark = '演示初始额度'` 的分录（与平台侧成对，逐业务号守恒）。新注册用户从 0 开始，可在「我的」页面自助模拟充值。

**账户余额为什么允许负数**：只有 `EXTERNAL` 会为负 —— 它记录「一共从系统外部净流入多少钱」（模拟充值 + 管理端加款），是外部资金在账上的镜像，不是平台的资产。用户账户由 `ck_account_balances` 卡死为非负。

## 6. K 点约束落地对照

| 硬指标 | 业务约束 | 数据库层怎么保证 | 应用层还要做什么 |
| :-- | :-- | :-- | :-- |
| **K2 时段冲突** | 同一物品同一时段只能有一笔有效订单 | `uk_occupancy(item_id, occupy_date)`（逐日展开） | 预检 → Redis 锁 → 事务插入；`DuplicateKeyException` 转 4090 |
| | 自租禁止 | `ck_order_bilateral` | Service 先返回 3006 |
| | 占用与状态严格同步 | `A2/A3/A4` 断言（占用行数 = 租期天数，**含 `PENDING`**；终态无占用；**`PENDING` 必须有占用**） | 建单即逐日 `INSERT`；进入终态（`COMPLETED` / `CANCELLED`）必须 `DELETE` 占用。⚠ 若把 `PENDING` 排除在占用之外，待确认期间同一时段能被重复下单，`uk_occupancy` 没机会拦，K2 直接破 |
| **K3 费用结算** | 金额精度 | 全库 `DECIMAL`，`A9` 断言无 float | BigDecimal + HALF_UP |
| | 改价不影响历史订单 | 三个价格快照列 | 查询一律取订单快照，不 join item 现价 |
| | 结算幂等 | `uk_settle_order` + `uk_settle_no` | 重复结算捕获冲突返回 4003 |
| | 应退不为负 | `ck_settle_amounts`（`refund_deposit >= 0`） | `max(..., 0)` |
| **K4 信誉分** | 分值边界 | `ck_user_credit`（0..100）+ `ck_credit_range` | 计算后 clamp |
| | 不重复加减分 | `uk_credit_biz` | 捕获冲突视为已记过 |
| | 可回溯 | `credit_log` 存 before/after | 每次变动必写流水，禁止只改 `user.credit_score` |
| **K6 损耗检修** | 权重与累计值范围 | `ck_loss_weight`（0..1）+ `ck_loss_state` | `w` 保留 4 位，`L` 截断到 [0,1] |
| | 阈值行为可追溯 | `loss_log.action` | 达 0.6 提醒保养、达 0.85 置 `MAINTAINING` |
| **账务（新增）** | 一个主体一个账户 | `uk_account(owner_type, owner_id)` | 账户懒创建时靠它防重复插入 |
| | 同一业务同一动作只入账一次 | `uk_entry_biz(biz_type, biz_id, action, from_account_id, to_account_id)` | 结算/冲正重入直接冲突，服务层视为已记 |
| | 按单查账 / 按人查账 | `idx_entry_order(order_id)`、`idx_entry_from(from_account_id, created_at)`、`idx_entry_to(to_account_id, created_at)` | 钱包页按时间倒序、订单详情看资金轨迹 |

## 7. 刻意取舍（答辩会被问到的 11 个点）

1. **订单表叫 `rental_order` 而不是 `order`**
   `order` 是 SQL 保留字，用它意味着全库每条 SQL 都要反引号，MyBatis-Plus 也要 `@TableName("`order`")`，出错面大。`rental_order` 语义更明确且不破坏 §5 命名规范（单数、lower_snake）。已在需求总结 §14.1 偏差记录备案。

2. **策略表用结构化单行表而非纯键值**
   键值表把 `0.5` 存成字符串，读出来必须解析 + 容错，容易出现 "abc" 这种脏值；结构化列让 MySQL 直接拒绝非法类型，还能写 `CHECK` 保证区间自洽。零散异构参数仍用键值表，两种形态并存是有意的。

3. **`credit_log` 加 `uk_credit_biz(user_id, order_id, reason_code)`**
   需求总结只要求"绑定订单"，但**幂等**是隐藏需求：定时任务重跑、用户连点两次"确认归还"都会导致双倍加减分。唯一键让重复写入变成数据库错误而不是脏数据。

4. **不建物理外键**
   见 §2。补充一条公平的说明：外键能防孤儿行，唯一索引不能；所以本项目用"应用层禁止删主表 + 自检脚本跨表断言"替代，属于**用流程规范补技术约束**，代价是依赖纪律。

5. **不建 `order_status_log` 表**
   状态流转用订单表上的四个时间戳（`confirmed_at` / `in_use_at` / `completed_at` / `cancelled_at`）+ `cancel_reason` 表达，够答辩展示。真要完整时间线属于 P2，且可以用 `message` 表近似还原（每次状态变更都发一条站内信）。

6. **订单表冗余 `owner_id`**
   严格三范式应该 join `item` 拿出租方，但"我的租出"列表必然按 owner 过滤，join 一张大表只为取一个 id 不划算；且物品可能易主（本课题不支持转租，但模型不阻碍），下单时快照 owner 更符合"订单是历史事实"的语义。

7. **`user.deleted` 与 `uk_user_phone` 的冲突**
   软删后手机号仍占用，不开放二次注册。这是毕设取舍：换成"手机号+deleted 联合唯一"会导致同一手机号只能被删一次。真实产品该用"注销后手机号置为 `138****0000#deletedId`"，本课题不做。

8. **`item.cover_url` 与 `item_image` 并存**
   看起来是冗余（违反三范式），换来的是列表页**零 join 出图** —— 列表是最高频接口，每行多一次关联不划算。代价写在明处：改封面必须同事务写两处，因此加 `A16` 断言（封面必须等于 id 最小的图）防止两边漂移。

9. **"图片≥1" 只写在文档里，没有数据库强约束**
   MySQL 的 CHECK 只能看单行，无法表达"某物品在另一张表里至少有 1 行"。可选方案是触发器，但那会把业务规则藏进数据库、出错难查。所以这条交给发布接口（空列表 → `2001`），数据库只保留 `A15` 做数据巡检 —— **这是自觉的取舍，不是遗漏**。

10. **社区从自由文本改为字典表 `community`**
    原设计 `user.community` / `item.community` 都是 `VARCHAR(64)` 自由文本，"同社区"靠字符串相等。问题是同一个小区的三种写法（`阳光花园` / `阳光花园小区` / `阳光花园东区`）会被判成三个小区，等于把"就近"这个卖点做废。字典化后比较退化为 `community_id` 整数等值，改小区名只改一行。代价是多一张表、注册与发布要多一次下拉选择（顺带把"社区"从手输变成可选，输入错误归零）。已备案进需求总结 §14.1；**仍然不做地图与距离计算**（§10 边界不变）。

### 11. 为什么 `fee_flow` 与 `account_entry` 两张表并存

`fee_flow` 是**业务视角**（这张单产生了哪些费用项，方向 IN/OUT 相对"订单"而言），`account_entry` 是**账务视角**（钱从哪个账户到哪个账户，方向由 from/to 表达）。同一个结算动作会同时写两处，落在同一个事务里。

- 只保留 `fee_flow`：答不了"我的余额从哪来"，也就无法回答"钱是不是真的动了"。
- 只保留 `account_entry`：答不了"这单按哪几项收费"，结算单与账单对不上，答辩问「为什么收了 175」要现算。
- 双写代价：一次动作两次写入，任一侧失败整体回滚；用 `uk_settle_order`（结算）+ `uk_entry_biz`（账务）两道幂等键兜住重入。
